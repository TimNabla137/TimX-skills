# 时间与任务管理

目标：每日推进一项主要成果，在真实容量内兑现承诺，减少切换、顺延和晚间补工。先读当前项目 AGENTS.md；作用域、语言、时区、作息、容量比例、完成报告处理和写入授权均由项目或当前会话提供。本 Skill 不携带个人配置或既有授权，也不自行创建定时任务。

## 1. 获取足够且当前的输入

- 通过 Lark CLI 用户身份（`--as user`）读取当前未完成待办、个人 OKR 及目标日期日历；先查相应帮助或 schema，不猜命令和资源 ID。任务操作按 lark-task，文档或 Base 按对应 Skill，认证问题按 lark-shared。只有当前周期为空时，不把旧周期自动当作当前目标。
- 列表需核对分页、所属范围和状态；有任务 GUID、资源入口时直接复用。只对候选任务补读描述、依赖和必要历史，不逐条深挖全部积压待办。保留已有日历的任务关联，避免重复排程。
- 标明来源、读取时间及范围缺口。区分服务端状态、用户报告、推断、假设和 UNKNOWN。读取失败不把未知时段当空闲；OKR 为空不等于没有长期目标。正文截止和系统字段冲突时暂停依赖该日期的决策。
- 只问无法从当前消息、项目规则及可读资料确定且影响安排的问题，集中询问；不要反复确认已知偏好或同一授权。历史日历仅证明安排，不证明实际投入。

## 2. 任务评估与 Eisenhower Matrix

对纳入规划的任务形成足够启动的记录：预期结果、下一步、完成标准、截止及其来源、依赖、剩余净工作量和专注要求。不要求把全部积压事项展开为项目计划。

先判断可执行性：可直接执行／等待依赖／需要澄清。等待他人的工作仅安排自己能推进的部分；目标不清时安排有明确问题与产出的探索块，探索结束再估计，不能凭标题给精确耗时。

分别判断重要性与紧急性：前者依据目标贡献、交付价值和不做的后果，后者依据已确认截止、剩余可用时间及依赖时效。任务长、消息多或系统填有日期本身不足以证明重要或硬截止。

| 象限 | 排程决策 |
| --- | --- |
| 重要且紧急 | 优先安排截止前可完成的阶段；容量不足则说明承诺冲突 |
| 重要不紧急 | 主动保护连续工作块，避免长期被琐事挤占 |
| 紧急不重要 | 简化、集中办理或建议委派；未经授权不联系他人 |
| 不重要不紧急 | 建议暂缓或取消，未经明确要求不删除待办 |

用户指定重点优先。象限有疑问就标暂定，不构造复杂分数；结合截止可行性和依赖选择当天一项主要成果。“必须完成”只用于已确认承诺或硬截止。

## 3. 估时：区间、依据与剩余量

- 给出剩余净工作分钟区间、预计番茄数、依据和主要不确定因素；优先采用用户报告或可核实的同类实际耗时，没有依据标为初估。
- 默认每番茄工作 25 分钟、短休 5 分钟，连续四个后以 15–30 分钟长休替代短休；用户习惯优先。番茄数用净工作分钟除以单次工作时长向上取整。小任务可在同一番茄内合并，不逐项向上取整导致夸大。
- 净工作量、块内休息和日历占用分别列算。日历块占用＝计划净工作＋实际安排的块内休息；块尾休息若放在块外只扣一次，不机械给每个块追加长休。
- 选取区间内用于排程的具体时长并说明依据；不确定且截止紧时采用较保守估计或先探索。承诺风险按区间上沿检查，不用乐观值掩盖缺口。
- 超时或顺延先核对已完成部分和范围变化，再估剩余量，不能直接重排原始总时长。无实际耗时证据时不能用事件长度校准。

## 4. Time Blocking：容量与位置

先划定尚未过去的工作窗口，合并重叠的固定日程、用餐及不可用时段后扣除；全天事项依据真实忙闲含义处理，不把日期标签直接算作整天占用。已有任务工作块需计入总负荷，不能既当固定占用扣掉，又作为任务重复新增。

容量按项目规则计算，并写清分母：可用工作窗口减固定占用及用餐等不可用时段为可分配窗口；按项目预排比例限制任务净工作总量。块内休息必须另计且总日历占用不得超过窗口，保留的余量用于临时事项、超时和转换，不再重复按同一比例扣减。已有工作块计入净工作预算；若项目另有口径则遵从并注明。缺少精确净工作量时采用标明假设的估计，不据此断言超载。

- 先安排主要成果与已确认承诺，再安排其他任务。深度工作放在已知合适的精力时段；未知时按可用连续窗口选择，不假定用户早晨效率最高。
- 同场景或工具的琐事集中成块，列明关联任务及各自估时；长任务按可验收阶段分块。周期任务仅用已确认频率与重复范围，并检查每次实例的冲突。
- 每个块让用户一眼看清做什么、何时结束和推进到哪里：任务／阶段标题、起止时间、任务链接或 GUID、动作、产出、净工作估计及休息节奏。通常一个工作块一个事件，不为每个短休建事件。
- 任务阶段须落在实际可用的连续窗口内。区间上沿无法在截止前容纳时报告风险；排不下的事项列明推荐顺延项、原因和承诺影响，不塞满日历，不自动延伸到晚上。

## 5. 触发式重排与完成报告

临时急事、超时、提前完成、依赖或精力变化时：确认变化 → 更新剩余量和截止风险 → 优先使用尚可用的预留余量 → 只调整受影响的未来工作块。先给推荐取舍；涉及已确认承诺冲突才交用户决定，不把普通可恢复的排程细节全交用户选择。提前完成可保留空闲，不自动填满。

保护固定日程和未受影响的工作块，保留过去记录。周期任务冲突优先处理对应实例，不无意修改整个系列。用户说“只盯进度”时只核对状态和调整计划，不接管制作交付物。

用户报告完成时先遵循项目或当前会话的明确规则：如已授权将明确完成报告视为关闭指令，唯一匹配后执行并读回，不额外索要证据；阶段完成、指代不清或仍在进行中不关闭整项。没有这类授权时不推断写入许可。记录为用户报告，不能声称产物或付款等外部事实已独立核验。

## 6. 日历与待办写入、对账

仅在明确授权的日历、日期和字段范围内执行；安装或调用 Skill 不构成授权。“只给建议”“先别写入”优先。优化 Skill、模拟验证不等于请求真实排程。

1. 写入前刷新相关任务和目标时段，检查忙闲冲突、同任务同阶段的已有事件及任务完成状态。复用或更新仍在授权内的本助理工作块；无法读取忙闲则暂停依赖它的写入。不覆盖无关日程、不添加参与者或对外邀请。
2. 新增、改期或取消工作块后，以及修改任务计划日或完成状态后，按任务 GUID 对账：任务是否存在、完成状态、计划开始日、截止、事件任务链接及有效未来工作块。已授权的计划开始日和排程说明同步后分别读回；多段任务的开始日可早于首个工作块，不强制等于每一段日期。
3. 截止是交付承诺，不随排程改期；完成状态按完成报告授权处理，不随事件结束自动改变。用户报告与服务端状态不一致时应用当前授权核对处理；已完成任务的未来工作块先核对是否仍需，再按范围取消，不自动删除整套周期日程。
4. 读回确认事件 ID、任务关联、起止时间、时区及重复规则。超时或响应未知先查是否已生效，再重试；部分成功逐项报告，不盲目重复创建或宣称全部同步。不得用默认描述覆盖原有无关任务内容。

## 7. 晨间、复盘与简短输出

晨间：确认尚未知的精力和临时事项，给出今日主要成果、任务估时与可执行日历，只列必要的待决定冲突。提醒明日及本周已确认的交付或硬截止，没有则如实说明；不重复整个积压列表。

晚间：对照计划、用户报告、可读产物和剩余量，记录主要成果、可确认的连续专注时间、顺延原因、晚间工作和精力感受。区分估时不足、临时插入、依赖阻塞、范围变化与其他已知原因，未知就保留未知。不以勾选数量或日历占用衡量效率，不自动安排晚间补工。

复用当前会话及项目既有记录，只保留能影响下一次安排的信息，不新增繁琐台账。用可信反馈校准同类任务；规则验证通过不代表真实效率改善。实际效果可低负担比较主要成果完成、承诺风险、顺延原因、估时偏差、晚间补工及用户调整负担，控制任务难度和可用容量差异，不编造提升比例。

结论先行，按需显示主要成果、估时依据、日历工作块、未排事项和需用户决定的冲突；区分建议、已写入、用户报告、UNKNOWN 与 NOT_RUN。写入后简报结果与未解决差异。定时讨论由现有自动化工具读取配置决定，不因 Skill 调用创建提醒。
